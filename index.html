01 / UNDERSTAND THE SIGNAL

What is DNS change monitoring?

DNS change monitoring repeatedly checks selected DNS records against values you have accepted. A lookup answers “what is published now?” A monitor adds “is that still the configuration I expect?” Useful DNS change alerts preserve the before and after, the queried name and type, the observation time and any lookup failure.

01

Choose a baseline

Inventory the exact names and record types you depend on. Review the answers before accepting them; the first result is not automatically correct.

02

Compare the answers

Compare record sets rather than raw response text. Keep successful empty answers, NXDOMAIN, SERVFAIL and timeouts distinct.

03

Review the change

Match the observed change to a release or provider migration. Accept a new baseline only after checking that it is intentional.

DNS monitoring and uptime answer different questions. HTTP health checks can stay green after an A record changes, or while MX records route mail somewhere unexpected. Use both when both signals matter.

03 / QUERY THE SOURCE

How to monitor DNS changes with authoritative lookups

Use dig from BIND’s DNS utilities on macOS or Linux, or inside WSL on Windows. Replace the example domain with one you manage. Run the commands manually first and check response status before automating comparisons.

Find the nameservers, then query each one

Shell / dig
# Discover NS hostnames through your configured resolver.
dig example.com NS +short

# Query every discovered server, preserving status and flags.
for ns in $(dig example.com NS +short); do
  printf '\n--- %s ---\n' "$ns"
  dig @"$ns" example.com A +norecurse +noall +comments +answer
done

Look for the aa flag on an authoritative answer and inspect the response status. If servers disagree, record each answer separately and investigate the deployment. Discovery through a resolver can itself be cached; for delegation diagnosis, inspect the chain with dig +trace example.com NS.

Extract values for a focused comparison

Single server / single type
# Replace ns1.example.net with a real authoritative server.
dig @ns1.example.net www.example.com A +norecurse +short

# Check mail routing and policy separately.
dig @ns1.example.net example.com MX +norecurse +short
dig @ns1.example.net example.com TXT +norecurse +short

+short is convenient for extracting values, but an empty output does not tell you whether the name is missing, the type is absent or the query failed. Keep the full status-bearing response as evidence. CNAME chains can also appear in short output; use the full answer to identify which RRset changed.

Authoritative state is not a propagation measurement. A changed authoritative answer can coexist with older cached answers until their TTLs expire. For a user-visible incident, also query the recursive resolvers your users depend on.

A baseline checklist for your repository

  • Store the queried name, type, expected values, authoritative server and UTC capture time.
  • Keep lookup errors outside the accepted-value file; a timeout must never replace a healthy baseline.
  • Sort multi-value answers before comparing them; TTL countdowns are not record-value changes.
  • Treat TXT strings and record-specific fields carefully. Do not blindly lowercase all DNS data.
  • Review intentional changes through your normal deployment process before updating expected values.
  • Document the polling interval and owner. A scheduled check cannot guarantee instant detection.

For protocol details, see RFC 1035: DNS implementation and specification and the official BIND dig reference.

04 / MAKE ALERTS ACTIONABLE

A DNS change alert should tell you what to do next

Common observations and the next investigation step
ObservationCheck next
A / AAAA address changedCompare with the deployment or CDN change. Check both IPv4 and IPv6 paths.
CNAME target changedConfirm the target belongs to the intended service and inspect the rest of the chain.
MX or mail-policy TXT changedCompare the mail provider’s intended configuration. A responding website does not prove mail routing is correct.
NS set changedCheck both the child-zone NS answer and the parent delegation. They are separate measurements.
SERVFAIL or repeated timeoutsPreserve the last good baseline. Check each authoritative server and DNSSEC validation separately.

During an incident

  1. Capture: save the full response, server, UTC timestamp and accepted values.
  2. Correlate: check the release log, registrar changes and DNS-provider audit trail.
  3. Verify: query each authoritative server, then relevant recursive resolvers.
  4. Resolve: restore the intended configuration through the responsible provider, or accept the verified planned change.

A public DNS answer cannot identify who edited a record or establish malicious intent. Preserve your provider’s audit logs for attribution.

OPERATOR NOTES

Questions developers ask

Can I monitor DNS changes with a cron job?

Yes. Schedule authoritative queries, check their status, normalize each record type and compare successful answers against a reviewed baseline. You also need durable state, failure handling and alert delivery. The commands above are a diagnostic starting point, not a production monitoring daemon.

Does every DNS difference need an email?

No. Reordered values and changing cache TTLs can produce text differences without a configuration change. Define record-specific comparison rules, distinguish errors from missing records, and decide when a repeated failure deserves escalation.

Can a scanner discover every record in a zone?

No. Query-based discovery only finds the names it asks for. Inventory your applications and providers, include known subdomains and DKIM selectors, and use an authorized zone export where available.

Is DNS Notify the DNS NOTIFY protocol?

No. The hosted product is separate from the primary-to-secondary DNS notification mechanism in RFC 1996. This guide discusses observing public DNS changes.
