DNS MONITORING / DEVELOPER GUIDES

How to monitor DNS changes

To monitor DNS changes, inventory the records you depend on, capture a reviewed baseline, query authoritative servers on a schedule and compare successful answers without overwriting the expected state.

Define what “changed” means before you schedule a job

For a web hostname, the monitored object might be the A-record set for api.example.com. Its expected values are separate from its availability. A successful lookup that returns a different address is a change; a timeout is a failed observation. Treating both as an empty string loses the distinction the operator needs.

Choose a capture location and document it. A recursive query represents what that resolver currently knows. A direct authoritative query inspects the server supplying the zone data. Neither alone measures every user’s experience, and different authoritative servers may briefly disagree during a deployment.

1. Build an explicit record inventory

List each owner name, record type, expected RDATA set, service owner and change source. Include both the apex and service hostnames where appropriate. DNS does not provide a general “show me every name” query; a scanner is an aid to discovery, not proof that the inventory is complete.

2. Capture a reviewed baseline

Save a successful status-bearing response from every authoritative server you intend to watch. Record the UTC time and the server queried. Compare the result with your provider’s intended configuration and application requirements before accepting it. A first observation can capture an existing error just as easily as a healthy state.

AUTHORITATIVE DNS LOOKUPS

How to monitor DNS changes with authoritative lookups

Use dig from BIND’s DNS utilities on macOS or Linux, or inside WSL on Windows. Replace the example domain with one you manage. Run the commands manually first and check response status before automating comparisons.

Find the nameservers, then query each one

Shell / dig
# Discover NS hostnames through your configured resolver.
dig example.com NS +short

# Query every discovered server, preserving status and flags.
for ns in $(dig example.com NS +short); do
  printf '\n--- %s ---\n' "$ns"
  dig @"$ns" example.com A +norecurse +noall +comments +answer +authority
done

Look for the aa flag on an authoritative answer and inspect the response status. If servers disagree, record each answer separately and investigate the deployment. Discovery through a resolver can itself be cached; for delegation diagnosis, inspect the chain with dig +trace example.com NS.

Extract values for a focused comparison

Single server / single type
# Replace ns1.example.net with a real authoritative server.
dig @ns1.example.net www.example.com A +norecurse +short

# Check mail routing and policy separately.
dig @ns1.example.net example.com MX +norecurse +short
dig @ns1.example.net example.com TXT +norecurse +short

+short is convenient for extracting values, but an empty output does not tell you whether the name is missing, the type is absent or the query failed. Keep the full status-bearing response as evidence. CNAME chains can also appear in short output; use the full answer to identify which RRset changed.

Authoritative state is not a propagation measurement. A changed authoritative answer can coexist with older cached answers until their TTLs expire. For a user-visible incident, also query the recursive resolvers your users depend on.

A baseline checklist for your repository

  • Store the queried name, type, expected values, authoritative server and UTC capture time.
  • Keep lookup errors outside the accepted-value file; a timeout must never replace a healthy baseline.
  • Sort multi-value answers before comparing them; TTL countdowns are not record-value changes.
  • Treat TXT strings and record-specific fields carefully. Do not blindly lowercase all DNS data.
  • Review intentional changes through your normal deployment process before updating expected values.
  • Document the polling interval and owner. A scheduled check cannot guarantee instant detection.

For protocol details, see RFC 1035: DNS implementation and specification and the official BIND dig reference.

3. Make polling preserve evidence

Schedule checks only after the manual queries behave as expected. Keep accepted values, latest observed values and observation status as separate fields. If a check fails, record the failure and retain the accepted values. Do not silently rewrite the baseline on every run: that turns change monitoring into a last-result cache.

A useful observation includes the domain, owner name, type, server, UTC timestamp, status, answer values and TTL. TTL belongs in the evidence even if TTL-only differences are excluded from value-change alerts. Define normalization separately for each record type; use the false-positive checklist before comparing responses.

4. Choose the detection window deliberately

The time between checks limits how quickly a change can be observed. A record can change and revert entirely between two successful checks. Failed lookups and delivery delays can extend the detection window further. Describe your actual schedule rather than promising instant DNS change detection.

5. Exercise the complete loop

On a domain you control, make one planned change and confirm that the next observation preserves both values. Test an unchanged answer in a different order. Test a failed lookup without deleting the last good baseline. Finally, verify alert delivery and who receives it; a comparison that works in a terminal is not a complete alerting system.

6. Review and accept planned changes

Match the observed value to an approved release or provider change. Verify the public answers, update the expected state and record who reviewed it in your change process. For an unexplained difference, investigate first. DNS data alone cannot tell you who made the edit or whether it was malicious.
