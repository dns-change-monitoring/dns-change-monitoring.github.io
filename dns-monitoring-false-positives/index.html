DNS monitoring false positives

Reduce DNS change monitoring noise by distinguishing meaningful record changes from response ordering, cached TTLs, presentation differences and failed observations.

Published by DNS Notify · Reviewed 7 November 2026 · View source

Compare DNS meaning before you compare raw text

DNS change monitoring gets noisy when a presentation difference is mistaken for a configuration change. A good comparison policy defines the owner name, record type, query source and normalization rules. It also preserves the unmodified response so an operator can revisit the evidence.

There is no safe universal “clean up every DNS answer” function. Sorting address records is straightforward; changing TXT case or discarding MX preferences can erase a meaningful difference. Make comparison rules explicit and test each one with examples.

1. Record order is not record identity

An A-record answer containing two addresses can arrive in either order. Compare the RRset as a set rather than comparing the printed answer line by line. The local comparison tool demonstrates ordering and duplicate-line handling.

2. Cached TTL countdowns are not changed destinations

A recursive resolver normally returns a decreasing remaining TTL as its cached data ages. A diff of the whole printed response can therefore change while the RDATA remains identical. Store TTL as evidence and decide separately whether you want configuration-TTL alerts. Do not erase TTL from diagnostic captures simply because you exclude it from value-change notifications.

3. TXT content is not a DNS hostname

Do not blindly lowercase every value. TXT records can carry verification tokens and application-specific data. A TXT RR can also contain multiple character-strings that lookup tools display with quotation marks. Parse the DNS record structure before comparing a reconstructed application value; never collapse internal whitespace across all TXT data.

4. CNAME chains contain more than one observation

A short lookup can print an alias target followed by addresses from the target’s resolution. A changed target address is not necessarily a changed CNAME record. Keep each owner name and type separate, and record where each answer came from.

5. Missing, failed and empty are different states

NXDOMAIN is a name-error response. If a CNAME chain is present, inspect which name in the chain is missing rather than assuming the original alias is absent. A successful NOERROR response without the requested RRset is different. SERVFAIL and timeouts are different again. A script that maps all four cases to an empty file can report a deletion during an outage and silently erase the expected baseline.

6. Different sources can legitimately disagree

A resolver with cached data and an authoritative server with new data may return different values during a migration. Different authoritative servers may also be at different deployment stages. Compare observations from a documented source and inspect server disagreement explicitly; do not combine unrelated vantage points into one unexplained record change.

7. SOA serials need a deliberate policy

An SOA serial can change when another part of the zone is edited. Whether that deserves an alert depends on whether you are watching zone activity or the SOA’s other fields. DNS Notify masks the serial for its SOA comparison. That is a documented product choice, not a protocol rule that every monitor must follow.

False-positive prevention checklist

  • Capture owner name, type, server, UTC time and response status with every observation.
  • Compare values only after a successful, understood response.
  • Keep the last good accepted state when a lookup fails.
  • Use type-specific parsing; preserve TXT data and MX preference values.
  • Decide explicitly whether TTL-only and SOA-serial-only differences should notify.
  • Test reordered answers, repeated values, missing records and failed queries separately.
  • Retain raw evidence even when your comparison ignores a field.

A quiet monitor should still preserve meaningful changes. Suppressing every difference prevents noise by removing the signal as well. Define the behaviour, test it and document it for the person receiving the alert.

IMPLEMENTATION CONTRACT

A record-aware DNS change monitoring comparison

Use an explicit comparison key. For ordinary Internet DNS records, that includes the fully qualified owner name, class and type. Keep the query source and observation status alongside that key. A CNAME RRset and the A RRset at its target are separate objects, even when one lookup prints both.

key = (canonical_owner_name, dns_class, record_type)
observation = (queried_server, observed_at_utc, rcode, answer)

if observation_is_transport_failure:
    record_failure(key, observation)
    keep_accepted_baseline(key)
elif rcode == NXDOMAIN:
    record_negative_response(key, observation)
elif rcode != NOERROR:
    record_dns_error(key, observation)
else:
    rrset = select_answer_rrset(answer, key)
    compare_using_type_specific_rules(accepted[key], rrset)

# A missing requested RRset still needs CNAME/referral analysis.
# No observation automatically overwrites accepted[key].

This is an illustrative state model, not executable production code. A NOERROR response with no requested RRset can require further interpretation: an alias, a referral or a negative type answer are not interchangeable. Preserve the complete response, including authority-section data when relevant.

Canonicalize names without rewriting opaque data

DNS-name comparison is case-insensitive for the ASCII letters in names, but that does not make every field of every RDATA value case-insensitive. Use a DNS-aware library for embedded names and wire-format parsing. Preserve opaque bytes, TXT character-strings, numeric fields and application-specific semantics rather than applying a global lowercase or whitespace operation.

Make negative caching visible

Resolvers can cache negative answers as well as positive answers. Creating a previously missing name does not mean every resolver will immediately return it. Capture the negative response and relevant SOA data, then compare authoritative state with the recursive vantage point separately. See RFC 2308 on negative caching.

Keep validation scope explicit

An authoritative answer with the AA flag identifies an authoritative response; it does not by itself establish DNSSEC validation or prove that every server has the same zone contents. If validation failures are in scope, define a separate validating-resolver check and record its result. A raw value diff should not be labelled a DNSSEC audit.

Protocol references: RFC 2181 on RRsets and DNS clarifications and RFC 4343 on DNS case insensitivity.
