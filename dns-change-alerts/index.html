What should a DNS change alert contain?

A useful DNS change alert names the record, shows its accepted and observed values, identifies the queried server and timestamps the observation. It distinguishes a value change from a failed lookup and gives the recipient a clear first investigation step.

“DNS problem detected” sends the operator back to discovery. “The A-record set for api.example.com changed from 192.0.2.10 to 192.0.2.20” preserves the difference that needs reviewing. Include the full answer separately when status flags or a CNAME chain are relevant.

A worked DNS change alert

Illustrative event — not a real customer alert
Observed (UTC): 2026-11-07T10:00:00Z
Name / type:   api.example.com / A
Queried server: ns1.example.net
Lookup status: NOERROR; authoritative answer
Accepted:      192.0.2.10
Observed:      192.0.2.20
Classification: value changed
Next step:     compare with the approved deployment

The address difference is evidence of changed DNS data. It is not proof of compromise, proof that the old address stopped serving traffic, or proof that all recursive caches have the new answer.

DNS CHANGE ALERT RESPONSE

A DNS change alert should tell you what to do next

Common observations and the next investigation step
ObservationCheck next
A / AAAA address changedCompare with the deployment or CDN change. Check both IPv4 and IPv6 paths.
CNAME target changedConfirm the target belongs to the intended service and inspect the rest of the chain.
MX or mail-policy TXT changedCompare the mail provider’s intended configuration. A responding website does not prove mail routing is correct.
NS set changedCheck both the child-zone NS answer and the parent delegation. They are separate measurements.
SERVFAIL or repeated timeoutsPreserve the last good baseline. Check each authoritative server and DNSSEC validation separately.

During an incident

  1. Capture: save the full response, server, UTC timestamp and accepted values.
  2. Correlate: check the release log, registrar changes and DNS-provider audit trail.
  3. Verify: query each authoritative server, then relevant recursive resolvers.
  4. Resolve: restore the intended configuration through the responsible provider, or accept the verified planned change.

A public DNS answer cannot identify who edited a record or establish malicious intent. Preserve your provider’s audit logs for attribution.

Route alerts by the action they require

Planned DNS change

Check the release ticket or provider migration record, then query the relevant authoritative servers. If the new public values match the intended state, accept the new baseline. Keep the alert as deployment evidence rather than treating every planned event as an outage.

Unexplained value change

Identify the service owner and preserve the response before making edits. Inspect DNS-provider and registrar audit logs using your normal access process. If the current configuration is wrong, restore the approved values through the provider responsible for the affected layer. A public monitor observes the result; it does not supply edit attribution.

Repeated lookup failure

Keep failure alerts separate from value-change alerts. Check whether the symptom is NXDOMAIN, an empty NOERROR answer, SERVFAIL or a transport timeout. Query other authoritative servers and relevant recursive resolvers before deciding how widely the failure is visible.

How DNS Notify handles DNS change alerts

DNS Notify keeps accepted and current record values separately. A difference marks the record pending, records both values and triggers an email. Accepting a verified value makes it the new baseline. If a value reverts before acceptance, the timeline records the reversion without a second email.

The published methodology describes four consecutive failed runs before a record lookup-failure email. Answer order and TTL-only changes are ignored for record-value comparison. A pass groups events into sections, and repeated-event emails are suppressed for three days. Check the current methodology for the full behaviour; an illustrative alert above is not a screenshot or promise of an exact email layout.
